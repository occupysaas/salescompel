# Plan 1 — Compatibility Specifications and Connector Test Laboratory

Status: offline laboratory implemented; live Salesforce verification remains pending. See [setup and evidence limits](../compat/README.md), [implementation record](../compat/implementation-log.md), [review follow-ups](plan-1-followups.md) and the [clean-room policy](../../CLEAN_ROOM.md).

## Summary

Implement the M0/M1 foundation without a Salesforce organization: a synthetic Sales Cloud/core-platform profile, traceable contracts, and a runnable open-source connector laboratory. SalesCompel is Apache-2.0 licensed and free to use. This phase does not implement the CRM backend, Vue application, migration engine, or external callout runtime.

## Implementation work packages

1. **Profile and evidence:** versioned pilot profile covering Account, Contact, a custom text field, external-ID upsert, administrator/restricted personas, language/locale settings and mandatory scenarios. API version remains unresolved until explicitly configured for live runs. Source register records URLs, dates, extraction status and claims. Contracts record IDs, preconditions, operations, assertions, normalization, source references and observation status. Separate synthetic examples from live evidence; never claim personnel-separated clean-room work without established separation.
2. **Connector harness:** independent Node/TypeScript workspace using JSforce, Salesforce CLI data/deploy-retrieve plugins and an isolated Python simple-salesforce check. Pin exact versions and lock dependencies; the profile records the exact connector versions. Provide validate, capture --target reference|candidate, compare and repeatability (two reference captures) commands. Credentials use environment variables/existing CLI authentication. Explicit endpoints, versions and disposable-environment acknowledgement are required. Missing configuration blocks the run with a nonzero exit status. Real interoperability calls never use mocked connectors.
3. **Executable scenarios:** describe; CRUD; repeated external-ID upsert; relationship query and pagination; composite failure and rollback readback; restricted field access; custom-field metadata deploy/retrieve; invalid field/query/missing record errors; dedicated-user language/locale update and restoration. Uniquely label synthetic fixtures, track every created ID and report cleanup failures. Never delete by broad filters.
4. **Localization:** separate product catalogs per Salesforce language/variant, registry/schema and validation fixtures. Check category, code mappings, direction, fallback, coverage, interpolation and independent locale/timezone/currency settings. Product translations and browser runtime remain future work. Specify custom-label import and canonical API-value preservation.
5. **Reports and CI:** versioned JSON plus Markdown reports with profile, API version, connector versions, timestamps, outcomes, assertions and provenance. Preserve nulls, values, ordering, errors and relationship identity. Only explicitly permitted generated IDs are normalized consistently. Reject mismatched versions/profiles. Outcomes are passed, failed, blocked and not_run. Offline CI checks types, tests, contracts, catalogs and locks; manual live jobs use credentials and cannot turn missing configuration into a successful verification.
6. **OpenAPI addition (user steering):** publish a validated OpenAPI 3.0.3 YAML contract for the initial REST surface. M2 will serve the contract; this phase validates the artifact only. Prepare JSON/YAML OpenAPI 3.0 External Services fixtures and documented compatibility contracts for registration, schemas, Named/External Credentials and Flow/Apex invocations; execution belongs to M7/M8. OpenAPI 2.0 is explicitly excluded. Search official Salesforce sources for reusable 3.0 YAML, pin provenance/hash/license, and test it when available. Do not mistake an External Services sample or a specialized API for the complete Sales Cloud REST contract. Org-generated specs require an org and remain pending.

## Interfaces and data flow

The pilot profile and source/contracts registry feed offline validation. Capture selects a target configuration, checks prerequisites, executes the same scenario functions through real clients, records sanitized observations, performs ID-scoped cleanup, and writes JSON/Markdown. Compare accepts reference and candidate reports, verifies provenance/profile/version/scenario and connector compatibility, and compares canonical observations and assertion outcomes. No capture or compare command may claim universal parity.

## Tests and acceptance

A fresh checkout installs locked dependencies and passes offline checks. Every scenario maps to a contract/client. Missing credentials yield blocked reports. Tests detect changes to status, permissions, null/omission, numeric values, relationship IDs and rollback; reject incompatible captures; redact headers/tokens/secrets; limit cleanup to owned IDs; detect missing catalog keys and parameter mismatches; validate OpenAPI 3.0 with unresolved references rejected and remote resolution disabled. Unit fixtures are labeled synthetic. Repeated reference captures are compared to separate deterministic behavior from required normalization. Runtime behavior and M0/M1 live-evidence completion remain pending until reference captures exist.

## Assumptions and handoff

Initial profile is synthetic Sales Cloud/core platform with endpoint/auth configuration changes allowed and unchanged connector business logic. Data Loader, Bulk API job lifecycle, connector-driven authentication/refresh, Pub/Sub, full migration, Apex/Flow runtime probes and browser execution follow later. The first live org needs dedicated users, fixture metadata, explicit API version and authorized synthetic writes. Locale inventory and Salesforce behavior are version-sensitive; documentary expectations are not certified behavior. The delivered laboratory is usable offline and ready for M2 endpoint implementation.
