# Plan 21 — Imported UI Hosting Feasibility Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

Status: proposed for maintainer review, 2026-11-03. Implementation not started.

**Goal:** Render and interact with a preserved three-file LWC-shaped bundle using an independent bounded interpreter and a synthetic record host, then publish a reproducible feasibility decision.

**Architecture:** Complete metadata, script and template validation produces an immutable model before host access or DOM changes. A scalar interpreter prepares state/events, a safe renderer prepares DOM bindings/patches, and one controller publishes successful actions and routes events to an immutable record binding. The browser harness is a separate Vite root, outside native product entry points.

**Tech Stack:** Existing web tooling only: Node compatible with >=22.12, TypeScript 5.9.3, Vite 7.3.7, Playwright 1.56.1; native DOM APIs and Node's built-in test runner; no new dependencies or manifest/lock changes.

**Spec:** [Plan 21 design](../specs/2026-11-03-plan-21-imported-ui-hosting-feasibility-design.md).

## Global Constraints

- Work directly on main.
- Use existing pinned web tooling only: Node compatible with `engines.node >=22.12`, TypeScript 5.9.3, Vite 7.3.7 and Playwright 1.56.1.
- No new dependencies, lockfile/manifest changes, copied Salesforce implementation/examples/assets, SDK/OSS engine imports, proprietary templates, customer source, live orgs, credentials or external communications.
- Existing tools are used through their APIs/commands, not copied into the experiment; `CLEAN_ROOM.md` is unchanged.
- No native UI route, Pinia store, production component, API/database/catalog, accepted profile/readiness/evidence, localization catalog, Plan 19 package/report or Plan 20 documents may change.
- Native product code must not import the experiment.
- Use a separate loopback-only Vite root and port 4181 with no product API proxy, no hosted deployment or end-user import/upload flow.
- All component source stays inert text: no eval, Function constructor, dynamic/module import of fixture JS, script/blob execution, raw HTML injection, DOMParser, or iframe executing imported source.
- Native shadow DOM supplies rendering/style separation only, not a security boundary.
- Host policy and records are synthetic client-side harness data, not authoritative tenancy/authentication.

## Review Focus

- Unsupported/trailing source in unused handlers, unfamiliar metadata or template attributes must fail before host read, DOM or listener publication (Tasks 2 and 5).
- Entity-encoded braces, prototype-like names and HTML-shaped property/event strings must remain literal data without changing parsed references or DOM capabilities (Tasks 2–5).
- Input updates must retain native node identity, focus/caret and per-instance private edits while public properties update independently (Tasks 4–6).
- Wrong-instance, stale or malformed events and denied host writes must not mutate other records; host denial preserves local edits rather than claiming whole-action rollback (Tasks 3, 5–6).
- Limits/cancellation after staged assignments or DOM preparation must publish no state/patch/event; disposed roots must be safely reusable without reattaching a native shadow root (Tasks 3–6).

## Shared interfaces and experiment decisions

These are private-to-experiment exports, not a production plugin API. Internal model representation is the builder's choice; public names/types below must match across tasks.

- `SourceBundle = Readonly<{ name: string; html: string; js: string; metadata: string }>`; no paths or extra files. Preserve/hash original UTF-8 strings; reject unpaired UTF-16 surrogates rather than silently replacing them during encoding.
- `Limits` has lower-camel-case numeric keys `bundleBytes, fileBytes, tokens, nesting, fields, methods, statements, templateNodes, stringBytes, steps, events`. `defaultLimits(): Limits` returns respectively `49152,16384,4096,32,16,8,64,128,4096,512,1`. All are positive safe integers, and events must equal 1.
- `Diagnostic` extends Error and exposes `code, phase, file, offset`; codes/phases/file tags and UTF-8 byte-offset rules are exactly the spec's. Its message contains only those fields; no raw parser/callback errors or source/data values.
- `Outcome<T> = { ok: true; value: T } | { ok: false; error: Diagnostic }`. Ordinary invalid source/data returns an Outcome, never an unstructured thrown exception.
- `compileBundle(bundle: SourceBundle, limits: Limits, signal?: AbortSignal): Outcome<Program>`; Program is an immutable, source-located model. Complete all three files and reference/type checks before returning success. Never dispatch on bundle/class names.
- `createMeter(limits: Limits, signal?: AbortSignal): Outcome<Meter>`; private Meter charge/check helpers and parser signatures are builder choices. Each action gets a fresh steps/events meter; compile uses byte/token/nesting/member/statement/node limits. Private per-invocation observer wrappers may emit phase labels for deterministic tests, never source values or global hooks.
- `initialize(program: Program, props: Readonly<Record<string,string>>, meter: Meter): Outcome<InstanceState>`; private immutable/replaced InstanceState contains per-instance public/private String fields. Run optional connectedCallback once. `prepareAction(state: InstanceState, method: string, inputValue: string | undefined, meter: Meter): Outcome<ActionPlan>` and `prepareProps(state: InstanceState, patch: Readonly<Record<string,string>>, meter: Meter): Outcome<ActionPlan>` prepare next state/ordered events without mutating the old state. ActionPlan/InstanceState shapes are defined in state.ts and consumed by component.ts. Do not expose real DOM/native events to these functions.
- `Identity = Readonly<{tenant:string;principal:string}>`, `Policy = Readonly<{identity:Identity;readAllowed:boolean;nameWriteAllowed:boolean}>`, `Account = Readonly<{tenant:string;id:string;name:string}>`.
- `createStore(rows: readonly Account[]): Outcome<SyntheticStore>`; store.snapshot(): readonly Account[] returns detached rows sorted by tenant/id. Validate nonempty tenant/ID, unique tenant-ID pairs and valid String data; identical IDs across tenants are allowed. Store size is trusted harness input.
- `bindRecord(store: SyntheticStore, identity: Identity, policy: Policy, recordId: string, owner: object, limits: Limits): Outcome<RecordBinding>`. The binding captures/copies context; `load(owner: object): Outcome<Readonly<{recordId:string;name:string}>>`, `receive(owner: object, event: ComponentEvent): Outcome<void>`, `close(): void`. `ComponentEvent = Readonly<{type:'save';detail:string}>`; runtime payload validation must reject extra fields, wrong type/non-String/oversize data. Unknown owner is denied; closed binding is disposed. Missing/denied read returns not-found/denied with no component mount. Only captured tenant/record Name can change; no source-supplied record ID or policy.
- `MountOptions` contains limits, optional signal and a trusted `onEvent(event: ComponentEvent): Outcome<void>` callback. `mountComponent(container: HTMLDivElement, program: Program, props: Readonly<Record<string,string>>, options: MountOptions): Outcome<MountedComponent>`. MountedComponent has `updatePublic(patch: Readonly<Record<string,string>>): Outcome<void>` and idempotent `dispose(): void`. If any source method can dispatch, require a callback before mount; source cannot access the callback itself. Renderer private `prepareMount`/`preparePatch` return detached nodes or trusted bounded publication plans; signatures/internal binding records are builder decisions shared with component.ts.
- `openRecord(container: HTMLDivElement, bundle: SourceBundle, context: Readonly<{identity:Identity;policy:Policy;recordId:string}>, store: SyntheticStore, limits: Limits, signal?: AbortSignal): Outcome<MountedComponent>`. Compile first, require the account profile's public fields exactly recordId/name, mint one opaque owner, bind/load then mount, and close binding on failure/disposal. A record controller rejects recordId patches; switch records by dispose/remount. Source rendering remains generic; only the explicit synthetic host profile maps recordId/name.

Inputs/context/limits are validated and copied before observers can mutate caller-owned objects; reject property maps larger than fields before copying, then enforce exact public keys on mount or known public-only keys on partial update. Empty strings are valid; Null/undefined/non-Strings are type errors. Source defaults initialize private fields; host supplies all public fields. Handler/lifecycle assignment targets must be private. Input and click method arities, event snapshots, literal/reference forms, full template/metadata allowlists, complete-source rejection and diagnostic taxonomy follow the spec.

On successful action, prepare state, all DOM patches and event queue, check cancellation, then publish state/DOM and deliver its single event. Runtime/budget/cancellation failures before publication restore prior model/DOM (including the browser-edited input's value) and deliver no event. Host denial/callback failure occurs after local publication: keep draft/DOM, preserve store and return a bounded host diagnostic. No cross-layer transaction is claimed. A disposed instance rejects updates and cannot deliver stale events; its empty experiment-owned root can be reused with a new owner, while foreign roots/active mounts are rejected untouched.

## Self-review and handoff

The seven tasks cover provenance/grammar, complete immutable source model, scalar preparation/host ownership, real DOM/lifecycle, source-first integration, repeated browser scenarios and reviewed scope/decision. Every Review Focus line has an owning test. Shared names/limits/state/publication contracts are defined once; rendered data never becomes executable source. Real browser execution is mandatory for a positive decision; no new runtime dependency or Plan 20 implementation is assumed.

Recommended execution method is inline via superpowers:executing-plans plus one fresh whole-change review: parsers, state and DOM publication share interfaces that benefit from one execution context. This is a recommendation, not an implementation instruction. This request creates only the spec and implementation plan; execution requires a separate request.
